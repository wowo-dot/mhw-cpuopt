# Handoff: MHW CPU cost project (2026-10-08)

Written at the end of a session in the sibling DLSS project
(`D:\mh world modding\dlssupdate`). Nothing has been built here yet: this
folder holds `AGENTS.md`, `.gitignore` and this note. Read `AGENTS.md` first.

## Why this project exists

The DLSS mod showed that MHW on the user's PC (RTX 5090, windowed 2560x1440,
240 Hz display) is limited by the CPU, not the GPU. DLSS alone therefore adds
little fps there; frame generation helps because it adds frames without CPU
submission. The user wants to know how much CPU time the game wastes and
whether a mod can recover it, mainly for players with weaker CPUs.

Expectation set with the user (an estimate, not a result):

- A perfect CPU fix on their PC is capped by the GPU at roughly +20% in the
  Alatreon fight and +35% at the hub (more in light scenes), with the DLSS
  mod's settings.
- Patching a few hotspots typically gives +5% to +20% in CPU-bound places
  (hubs). Rewriting the engine's renderer is out of reach for a mod.
- The deciding step is a profile of the game's own code. If a few functions
  dominate, a mod is worth building; if time is spread evenly, it is not.

## What is known about the engine (MT Framework)

Confirmed in the DLSS project for executable SHA-256
`c2ebbbd2c49f216d484e31a5219bed419eb1e5e7d206d02cba040a3ab79d90ea`
(PE timestamp `0x66D13CB6`). Verify again before relying on any offset.

- **Two-step rendering.** The engine writes draws as its own packets with
  32-bit sort keys, sorts them with a stable unsigned-key merge sort
  (RVA `0x23D2370`) and then translates each packet into Direct3D 12 calls.
  The per-context packet queue is an array of 16-byte entries
  `{u32 key, u32 pad, u64 packet}` at context+0x2B78 with the count at
  context+0x2B80 (dlssupdate `src/scaled_temporal/silhouette_probe.inl`).
- **Renderer and frame counter.** image+0x51C4480 points to the renderer;
  renderer+0x1F210 is the 64-bit frame counter, +0x1F208 the epoch
  (dlssupdate `src/bridge_probe/frame_packet.cpp`). The render context is
  renderer+0x710. Sampling the frame counter gives frame times without any hook.
- **Threads.** Game logic is cheap (about 0.6 ms). The render thread's
  submission is the main limit. Worker threads record some command lists, and
  in heavy views a worker can record a frame's final draw before the render
  thread records that frame's earlier passes.
- **Scale of work.** Thousands of Direct3D calls per frame; native queue walks
  of up to about 1,024 nodes per frame in the training grounds. Hubs (many
  NPCs) are the slowest scenes.
- **Protection.** The executable is protected; IDA uses the private decoded
  image. Protected code may show up in profiles as large regions without
  function boundaries. Its cost may be documented, never removed (`AGENTS.md`).
- **Prior art.** An old community mod (`!CRCBypass.dll`, "Performance Booster
  and Plugin Extender") removes the game's repeating CRC memory checks. The
  user considers it outdated; it is disabled in every MO2 profile and out of
  scope. "Tic Rate Fix" is a gameplay fix, unrelated.

More engine notes: dlssupdate `docs/research/` (start with `current-state.md`,
`performance-v012-result.md`, `shader-census-result.md`,
`postprocess-family-audit.md`, `multi-overlay-draws.md`).

## Reusable tools in the DLSS project

Copy and adapt; do not change the DLSS project from here.

- **Stack sampler**: `src/perf/sampler.cpp`/`.hpp`. About 1 kHz, in process:
  it suspends one thread at a time, unwinds with `RtlVirtualUnwind` against
  function tables read up front, never allocates or locks while a thread is
  suspended, and attributes the leaf, the innermost game frame and the
  innermost mod frames. It finds the Present thread through the DLSS mod's
  `frame_stats.hpp`; here it needs its own way to identify the render thread
  (for example the thread that advances the frame counter, or one Present hook).
- **Report**: `tools/profile_report.py` (symbols from a linker map for the mod,
  exports via dbghelp for system DLLs, game frames by RVA). For game
  attribution, export function starts and names from IDA on the decoded image
  into `local/` and map RVAs to functions.
- **Fast guarded reads**: the shared lock-free region cache in `src/perf/`
  (the DLSS mod's main CPU fix). Any in-process reader of game memory should
  use the same idea; one `VirtualQuery` per read, plus a module lookup per
  method check, cost the DLSS mod about 21 ms of render submission per frame.
- **Run handling**: `tools/mo2_slot.py` (install a test DLL into an MO2 mod
  folder with exact backups and a receipt) and `tools/evidence.py` (seal a
  finished run folder with a hash manifest).
- **Read-only external reader pattern**: `tools/read_scaled_haze.py` (process
  access limited to query and read).

## How DLLs get into the game

- Stracker's Loader (`dinput8.dll` + `loader.dll`) is enabled in the user's
  profiles; it loads DLLs from `nativePC\plugins`, later than the very first
  startup code.
- The DLSS mod is force-loaded by MO2: profile `barebonesdlss`
  `settings.ini` `[forced_libraries]`, executable entry
  "Monster Hunter: World - DLSS 1.2.110 test", library
  `D:\MO2\MHW\mods\dlssTEST\mhw_dlss_bridge_probe.dll`. The `dlssTEST` folder
  itself is disabled in that profile's modlist, which is expected.
- For profiling, loading as a Stracker plugin from a new MO2 mod folder is
  probably enough. Decide, document it, and keep it separate from `dlssTEST`.

## Suggested milestones

1. **Setup.** `git init`, CMake skeleton, a plugin DLL that logs a start event
   (executable hash, DLL hash, CPU model, loaded modules) and nothing else.
2. **Baseline.** Frame times without hooks (a thread sampling the frame
   counter, or one Present hook), percentiles per 5 s window, for each scene
   and configuration.
3. **Profiler.** The sampler adapted to sample the render thread, the main
   thread and the busiest workers, with game attribution via the IDA export.
4. **Hotspot report.** Top functions per thread and scene, with and without
   the DLSS mod. Answer: are there a few hotspots, and how much of the time is
   protection code?
5. **Decide with the user.** Only then pick candidate fixes; each one becomes
   a runtime switch measured A/B in the same scene.
